# Backend API Design Rules

RESTful API の設計規約。言語・フレームワークを問わず適用できる原則を記載する。

---

# 基本方針

- ベースパスを統一する（例: `/api`）
- リソース指向の URL 設計にする（動詞ではなく名詞を使う: `/orders` であり `/getOrders` ではない）
- URL パスは kebab-case（小文字・ハイフン区切り）を使用する（例: `/change-password`）
- レスポンス形式は JSON に統一する

---

# 認証・認可

- 認証不要なエンドポイント（ログイン・ヘルスチェック等）以外は、全エンドポイントで認証を必須とする
- 認証情報は `Authorization: Bearer <token>` ヘッダーで送信する
- ロール・権限による制御はエンドポイント（Controller/Router）の入り口で宣言的に行う（アノテーション/デコレータ/ミドルウェア等）。UI 側の表示制御のみに頼らない
- 初回パスワード変更やアカウント状態などの「強制フロー」がある場合は、専用フィルター/ミドルウェアで該当フロー以外を拒否する

---

# エラーレスポンス設計

詳細は [../error-handling.md](../error-handling.md) を参照。

- 通常のエラーは統一フォーマットで返す: `{ "code": "ERROR_CODE", "message": "..." }`
- バリデーションエラーはフィールド単位で返す: `{ "errors": [{ "field": "...", "message": "..." }] }`
- エラーコードは `SCREAMING_SNAKE_CASE` の文字列にする（例: `RESOURCE_NOT_FOUND`）
- エラーメッセージに機密情報・内部実装詳細を含めない
- ユーザー列挙攻撃を避けるため、「対象が存在しない」と「認証情報が誤り」を同一エラーにする（ログイン等）

---

# バージョニング・変更管理

- 破壊的変更を伴う API 変更は、既存クライアントに影響しないようパスまたはヘッダーでバージョニングする
- 非推奨化する場合は移行期間を設け、いきなり削除しない

---

# HTTP メソッド・ステータスコード

| メソッド | 用途 |
|---|---|
| GET | 参照（副作用なし） |
| POST | 新規作成・非冪等な操作 |
| PUT | 全体更新（冪等） |
| PATCH | 部分更新 |
| DELETE | 削除 |

- 作成成功: 201、更新・参照成功: 200、削除成功: 200 or 204
- クライアント起因のエラー: 4xx、サーバー起因のエラー: 5xx

---

# CORS

- 許可オリジンは環境変数等の設定値で明示的に管理する（ワイルドカード `*` を本番で使用しない）
