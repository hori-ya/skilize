# Backend Testing Rules

バックエンドの自動テストに関する規約。

---

# ファイル配置・命名

- テストファイルはテスト対象と対応させ、命名規則を統一する（例: `OrderService` → `OrderServiceTest`）
- テストコードはソースコードと同じディレクトリ構成をテスト用ルート配下に再現する

---

# テストの構成

- Arrange（準備）→ Act（実行）→ Assert（検証）の3段構成で記述する
- 1テストケースにつき検証観点は1つに絞る（複数の関心事を1テストに詰め込まない）
- テストデータは各テストケース内で完結させる（他テストへの依存・実行順序依存を作らない）

---

# レイヤー別のテスト方針

| 層 | テスト方針 |
|---|---|
| presentation（Controller） | リクエスト検証・レスポンス整形・ステータスコードを検証する。ビジネスロジックはモック化する |
| application（Service） | ユースケースの分岐・トランザクション境界を検証する。domain/infrastructure は必要に応じてモック化する |
| domain | ビジネスルール・不変条件を純粋なユニットテストで検証する（外部依存なし） |
| infrastructure | 実DB・外部APIとの結合テストで検証する（可能な範囲でテスト用コンテナ等を使用） |

---

# モック化の方針

- 外部システム（DB・外部API・時刻・乱数）はテストの決定性を保つためモック化する
- ドメインロジックそのものをモック化しない（テストの意味がなくなるため）

---

# コメント

- テストクラス自体には概要コメント（何を検証するテストか）を付ける
- ファイルヘッダー（著作権表示等）はテストファイルには不要とする（詳細は [../comments.md](../comments.md) を参照）

---

# カバレッジの考え方

- カバレッジ率そのものを目的にしない。分岐・異常系・境界値を優先してテストする
- 正常系1つに対し、異常系・境界値のケースを最低1つは用意する

---

# 短縮記法の制限（テストコードにも適用）

[code-style.md](code-style.md) の「短縮記法の制限」はテストコードにも適用する（ラムダ式・メソッド参照・Stream API・Optionalのメソッドチェーン・三項演算子・拡張switchを使用しない）。特にテストで書きがちな以下のパターンに注意する。

| 用途 | 禁止 | 代替 |
|---|---|---|
| 例外検証 | `assertThrows(XxxException.class, () -> service.method(...));` | try-catch文で呼び出し、catchブロック内で例外の内容を検証する（catchに到達しなかった場合は `fail(...)` を呼ぶ） |
| Mockitoのスタブ動作定義 | `when(mock.method()).thenAnswer(invocation -> ...);` | `Answer` インターフェースを実装したクラス（無名クラス可）を渡す。単純な戻り値指定（`thenReturn(...)`）はラムダを伴わないため対象外 |
| Stream を使った検証 | `assertTrue(list.stream().anyMatch(x -> x.isActive()));` | 拡張for文でループし、フラグ変数で判定してから `assertTrue`/`assertFalse` する |
