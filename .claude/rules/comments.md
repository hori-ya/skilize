# Comment Writing Standards

ソースコードの可読性・保守性向上を目的としたコメント記載規約。言語・フレームワークを問わず適用する。

言語・フレームワーク固有の記載例と追加ルールは以下を参照。

| 言語 / フレームワーク | ファイル |
|---|---|
| Java（Spring Boot） | [backend/comments.md](backend/comments.md) |
| TypeScript（React） | [frontend/comments.md](frontend/comments.md) |
| Python（FastAPI） | [ai/comments.md](ai/comments.md) |

---

# 目的

コメントは以下を補足するために記載する。

- 業務上の意図
- 設計上の理由（なぜその実装を選んだか）
- 処理の目的
- データ項目の意味
- 保守上の注意事項

## 優先順位

1. なぜその処理が必要なのか
2. 業務上どのような意味を持つのか
3. 何をしている処理なのか（コードを見れば分かる内容は書かない）

---

# 記載不要なコメント

コードを読めば自明な内容はコメントしない。

**悪い例**

```
// カウントを加算する
count++;

// ユーザーを取得する
const user = response.data;
```

---

# ファイルヘッダー

新規に作成する本番ソースファイルには、プロジェクトで定めた形式のヘッダーを記載する（機能ID・作成日・作成者・概要・更新履歴等、項目はプロジェクトごとに定義してよい）。

- 更新履歴は追記形式とし、既存の履歴を削除しない
- 更新履歴は最新の項目を先頭に追加する
- 「修正」「変更」等の曖昧な表現を禁止し、第三者が理解できる具体的な内容を記載する
- テストファイルにはファイルヘッダーを不要とする（クラス単位の概要コメントのみ付ける）

---

# クラス・コンポーネントコメント

以下を記載する。

- 役割（1行）
- 機能概要（2〜3行）
- 設計上の注意・制約（必要な場合のみ）

---

# 関数・メソッドコメント

- 公開（public）関数・メソッドには必須
- 限定公開（protected 等）には推奨
- 非公開（private）は複雑な処理のみ

記載内容: 処理概要、引数の意味（型で自明な場合は省略可）、戻り値の意味、例外が発生する条件（必要に応じて）

---

# 業務ロジックコメント

業務ルール・非自明な設計判断が存在する箇所には必ずコメントを記載する。

```
// 新規登録時は初回パスワード変更を必須にする業務ルール
```

---

# データ項目コメント

- エンティティ・モデルのフィールドには意味・制約を記載する（必須）
- リクエスト型はバリデーション制約が複雑な場合のみ
- レスポンス・結果型は意味が不明瞭なフィールドのみ

---

# 言語の使い分け

| 対象 | 言語 |
|---|---|
| クラス名・関数名・変数名 | 英語 |
| コメント | プロジェクトで統一した1言語（例外を作らない） |

---

# 更新履歴の記載ルール

```
YYYY/MM/DD 担当者名 #Issue番号（任意） 変更内容
```

- 最新履歴を先頭に追加する
- 過去履歴は削除しない
- 内容は具体的に記載する（曖昧な表現禁止）
- Issue がある場合は番号を記載する

---

# レビュー観点

- [ ] ファイルヘッダーが記載されている（本番ソースファイルのみ）
- [ ] 更新履歴が最新化されている
- [ ] クラス/コンポーネントコメントが存在する
- [ ] 公開関数・メソッドにコメントが存在する
- [ ] 業務ルールがコメント化されている
- [ ] コメントと実装内容が一致している
- [ ] 不要なコメントが記載されていない
