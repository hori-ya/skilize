# Frontend API Design Rules

フロントエンドにおけるバックエンドAPI呼び出しの設計規約。

---

# API クライアント

- HTTP クライアントは共通のインスタンス（インターセプター付き）を1つ用意し、feature 間で使い回す
- 認証トークンはインターセプターで自動付与する（`Authorization: Bearer <token>` 等）
- feature 固有の API 呼び出しは `features/{feature}/api/` に集約し、コンポーネントから直接 fetch/axios を呼ばない

---

# エラーハンドリング

詳細は [../error-handling.md](../error-handling.md) を参照。

- API エラーレスポンスの解析・翻訳は共通ユーティリティに集約する（feature ごとに重複実装しない）
- エラーコード → 表示メッセージの変換は一元管理された辞書・翻訳リソースを介する
- ユーザーに見せてよいエラーメッセージと、開発者向けの詳細情報を区別する

---

# 型定義

- API レスポンス・リクエストの型は明示的に定義し、`any` を使わない
- バックエンドの DTO 命名パターン（Request / Response 等）とフロントエンドの型名を対応させ、対応関係を追いやすくする

---

# 認証まわり

- 認証トークンの保存場所は1箇所に統一する（例: メモリ上の状態、または `localStorage`）。Cookie・localStorage・グローバル変数など複数箇所に分散させない
- トークン期限切れ時の挙動（再ログイン誘導等）を共通処理として実装する

---

# リクエスト設計

- 1画面が必要とするデータ取得は、意味のある単位の API 呼び出しにまとめる（画面表示のために大量の細粒度リクエストを発行しない）
- ローディング状態・エラー状態を呼び出し側で必ずハンドリングする
